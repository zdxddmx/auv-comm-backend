## 1. 为什么不能按"普通网络服务"来做

水下通信与岸上网络的差别是全方位的，**这些约束决定了后台必须怎么设计**：

| 水声通信的真实约束 | 对后台设计的影响 |
|---|---|
| 声速约 **1500 m/s** —— 2 km 距离**单程就要 1.33 s**，RTT 超过 2.6 s | 心跳超时不能按秒级设（本工程默认 3 s）；同步 RPC 不可用，必须异步 |
| 带宽低（常见 **9.6 kbps** 量级）—— 一帧 64 B 就要占用信道 **53 ms** | 帧头要短、批量上报要合并；信道是**串行占用**资源，得排队 |
| 丢包与抖动明显，受多径与噪声影响 | 必须做**序号连续性检测**、确认与重传、**冗余链路切换** |
| 链路可能长时间中断（上浮/下潜/遮挡） | 断线重连要**指数退避**，不能高频重试把信道打满 |

本工程用 `AcousticChannel` 把这三点显式建模（传播时延 + 串行发送占用 + 丢包抖动），
所以上层可靠性逻辑是在**真实约束下**被验证的，而不是在"零延迟无丢包"的假网络上跑通。

## 2. 目录结构（对齐通信后台的模块划分）

```
include/auv.h        统一公共接口
src/frame.cpp        帧协议：同步头 + 长度 + 序号 + 载荷 + CRC-16/CCITT
src/channel.cpp      水声信道仿真（时延/占用/丢包） + 通用内存链路
src/router.cpp       通信中间件：数据汇聚 / 指令分发 / 链路管理 / 可靠性 / 存储
src/main.cpp         仿真主程序：双链路 + 多航行器场景
test/test_auv.cpp    78 项单元测试
.github/workflows/   三平台 × C++17 编译 + 测试 + 跑仿真
```

| 模块 | 职责 |
|---|---|
| **frame** | 二进制帧编解码、CRC-16/CCITT-FALSE、**流式解帧**（粘包 / 半包 / 重同步） |
| **acoustic** | 水声信道：传播时延、发送占用、丢包与抖动（确定性随机，可复现） |
| **link** | 链路抽象（UDP / TCP / 串口 / 水声），统一 `send/recv/tick/stat`；可注入延迟与丢包 |
| **router** | 多航行器**数据汇聚**、岸基**指令分发**、**链路管理**与可靠性 |
| **可靠性** | 主备**冗余切换**、**指数退避重连**、**序号连续性检测**（丢包/乱序/重复）、事件日志 |
| **store** | 遥测 / 指令 / 链路事件落盘（journal 格式；可替换为 SQLite 后端） |

## 3. 帧协议

```
+--------+--------+--------+--------+--------+--------+--------+--------+
| sync0  | sync1  | type   | seq_lo | seq_hi | len_lo | len_hi | rsvd   |
| 0xEB   | 0x90   | 1 B    | -------- uint16 -------- | -- uint16 --    |
+--------+--------+--------+--------+--------+--------+--------+--------+
| payload (0..1024 B)                                      | CRC16 (2 B) |
+-------------------------------------------------------------------------+
```

- **CRC-16/CCITT-FALSE**（poly `0x1021`，init `0xFFFF`）—— 工业串口与水下遥测常用口径；
  自检值：`CRC("123456789") = 0x29B1`
- **序号**用于接收端做连续性检测，是发现丢包/乱序/重复的唯一手段
- **流式解帧器**处理真实串口/网络必然出现的粘包与半包，并对非法长度与坏帧做重同步

消息类型：`HEARTBEAT` / `TELEMETRY` / `COMMAND` / `ACK` / `EVENT` / `BULK`

## 4. 可靠性设计（岗位职责第 4 条）

```
        ┌──────────── 主链路 UDP（低延迟）───────────┐
岸基 ───┤                                          ├─── AUV
        └──────── 备用链路 水声（高延迟/丢包）────────┘
                 │
      ┌──────────┴──────────┐
      │  Router（通信中间件）│
      │  ① 链路健康监测      │  心跳超时 -> 判定失联
      │  ② 冗余切换          │  主链路不可用 -> 自动切到可用链路
      │  ③ 退避重连          │  尝试后**回读链路是否真可用**，否则退避翻倍
      │  ④ 序号连续性检测    │  丢包 / 乱序 / 重复分别统计
      │  ⑤ 事件日志          │  LINK DOWN / RECONNECT / FAILOVER / FAILBACK
      └─────────────────────┘
```

**两个容易被做错、本工程专门测过的点**：

1. **重连不能"假成功"** —— 传输层（网线/电台）不可用时，会话重连必须**回读真实链路状态**，
   否则会在断开区间里反复"成功—失败"震荡。本工程的 `Router` 重连后回读 `connected()`，
   失败则退避翻倍（0.5s → 1s → 2s → … 上限 8s）。
2. **指令帧不能当设备数据聚合** —— 只有 `TELEMETRY / HEARTBEAT / EVENT` 的载荷带设备头，
   `COMMAND / ACK` 载荷格式不同，混在一起解析会**凭空生成假设备**。

### 仿真场景

**normal**（双链路稳定）：

```
活动链路 : udp-shore      下发指令 24 条      接收 60 帧
链路 udp-shore        up=1  reconnects=0  failovers=0
链路 acoustic-backup  up=1  reconnects=0  failovers=0
```

**failover**（t=4s 注入主链路故障，t=8s 恢复）：

```
[t=4.0s] 主链路故障注入
[t=8.0s] 主链路恢复
活动链路 : udp-shore      下发指令 21 条
链路 udp-shore        up=1  reconnects=2  failovers=2
遥测入库 480 条 · 指令 21 条 · 链路事件 8 条

链路事件（journal）：
E,4.000000,acoustic-backup,LINK DOWN udp-shore (transport closed)
E,4.000000,acoustic-backup,FAILOVER udp-shore -> acoustic-backup
E,8.200000,udp-shore,LINK RECONNECT udp-shore (attempt 1)
E,8.200000,udp-shore,FAILBACK acoustic-backup -> udp-shore
```

**注意 4.0 ~ 8.0 s 之间没有任何"重连成功"事件** —— 传输层还没恢复，
重连尝试全部按退避挂起。这正是上面第 1 条要防的"假成功"。

## 7. 开发过程中被测试抓出来的问题

| # | 问题 | 定位方式 | 修复 |
|---|---|---|---|
| 1 | **断线重连退避失效**：把下次重试时刻设为"当前时刻"，同一 tick 内立刻重连，链路实际从没 down 过（重连次数被刷到 34 次） | `T5 router` 的"主链路被标记 down"用例失败 | 首次重试排到 `now + backoff_s`，失败后 backoff 翻倍 |
| 2 | **指令帧被当设备数据聚合**，凭空生成假设备（2 台变 3 台） | `T5 router` 的"设备数 = 2"用例失败 | 只有 `TELEMETRY/HEARTBEAT/EVENT` 参与设备汇聚 |
| 3 | **重连"假成功"**：`set_up(true)` 只改基类标志位，链路实现并未真正恢复，却在断开区间里反复 FAILOVER/FAILBACK 震荡 | 仿真日志里 4.0→8.0 s 出现 7 次切换 | 区分"传输层可用性"与"会话状态"；重连后**回读 `connected()`**，失败则退避重试 |
| 4 | **指令与链路事件没入库**（汇总恒为 0 条） | 仿真汇总与预期不符 | 主循环把可靠性日志转成链路事件写入 Store |

> 另有 2 处是**测试场景写错**（`poll()` 契约理解偏差、心跳超时时间点选得不合理），也一并修正。

## 8. 边界说明（重要）

- 本项目是**仿真与自建实践**，**未接入真实 AUV/ROV 与水声调制解调器**，不构成产品经验
- **水声信道是简化模型**：只有传播时延、串行占用与随机丢包，**不含多径、多普勒、
  时变信道与调制解调**（真机上这些由水声 Modem 处理）
- **链路抽象是内存实现**：`Udp/Tcp/Serial` 三类尚未接真实 socket 与串口，
  接口已按真实语义定义（`send/recv/tick/stat`），替换实现即可上真机
- **存储是 journal 落盘**：接口按 SQLite/MySQL 的用法设计（遥测/指令/事件三张表语义），
  但**未接真实数据库**（环境无 sqlite3 开发库）
- 未做**多线程/高并发**实现：当前是单线程事件循环，接口已预留（`poll` 按 tick 调用）
- 未做数据加密与鉴权

**下一步可做**：接真实 UDP/TCP socket 与串口（`termios`）；用线程池 + epoll 做并发收帧；
把 Store 换成 SQLite（遥测表按时间分区）；接入真实水声 Modem 做链路预算与重传策略调优。
